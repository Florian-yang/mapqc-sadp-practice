# 综合实践原始题干

来源：用户于2026年11月3日在本聊天提供。下文保留题干内容，优先于此前依据不完整材料形成的计划。

团队合作型作业

POI数据采集及核验移动应用 check@collect

（POI: Point of Interest，兴趣点，地图查询、定位操作重要的数据源：

房子、商铺、公交站、花坛、树木、景点等各类地表实体、现象的要素，有一定利用价值）

## 1、基本需求

采集者：

- 采集并传回 POI 照片、拍照位置、 POI分类及基本描述信息
- 拍照位置无需手动输入，由移动设备感知，随照片上传
- 根据后台要求重新采集

核验者：

- 发现错误后，标识出错POI，增加错误说明，保存到系统

地理信息平台支持（地图查询、显示、路径计算、导航）

- 在地图上按类别查询显示POI数据分布、错误标识及处理进展
- 使用地图导航功能，导航至指定POI位置

系统、用户间的通信（各类群发、点发）

- 系统向所有采集者群发通知消息，如提示因交通管制等暂停工作；
- 系统向所有核验者群发任务消息，如提示有新数据待检；
- 系统在核验者发现数据错误提交后，向采集者发消息通知数据质量问题
- 采集者复核后可选择重新采集、更新或驳回
- 采集者与核验者建立私聊讨论，交流错误标识详情，无法达成共识可将异议提交系统另行处理
- 系统收到异议处理请求后，向第三方工作人员发消息通知去现场重新采集、核验，核验结果为最后结果；系统发消息通知提交异议双方。
- 建立两个群聊：分别为采集者、核验者提供工作技巧、经验交流空间

平台或框架集成

- 地图服务平台：地图查询、显示 / 路径计算、导航
- 微信平台：绑定微信号、微信登录
- 文字识别 API：识别POI图像中的文字，如店铺招牌，辅助分类，等等

消息中间件

- 各类群发、点发

## 2. 注意事项

架构模式设计

- 运行环境：移动便携设备、Web、internet
- 可尝试（B/S, N层风格，移动、MVVM, MVC ……）

鼓励团队合作

- 每队成员不超过4人；
- 若组队完成，另需提交及各成员分工内容、比例说明；

## 3. 成果要求

1) 团队提交成果（文档、程序及演示）

- 架构设计 —— “一图二表”：各图使用适当UML表达
- 成果源码
- 演示：每组指派一人演示所设计实现的系统

2) 个人提交成果

- 每周进度小结（ 7 ~ 10/11周）
- 面馆升级后的计价小应用实现代码及类图（参加第四次作业）

1) 架构设计说明+进度周记（65%）

2) 软件源码包（15%）

3) 软件应用演示（15%）

4) 指定设计模式实现（5%）
